WS-M5-69 prospective design — bounded request residency for packed VLM allocations

Status: design and read-only audit only. WS68 remains a published valid rejection; best validated WS10 stays deployed. No source/build/model/performance change exists for69 yet.

Evidence and distinct hypothesis
Read prior32/33/56 residency reports and actual Context/Session/Model code. Those policies handle RAW BF16 masters; existing Begin explicitly rejects PrimaryReady with reason7, and coverage explicitly rejects packed weights. Original budget4GiB excludes full raw4B. Prior56 text-only admission failed whole-system preservation, and that rejection stands. Existing WS62 hardware-counter capture already covers BOTH models at steps4/16/28: reuse it instead of repeating an unchanged diagnostic. Its 4B warm ranks show MLP projections and vocabulary among substantial sampled custom intervals, not complete GPU shares. WS68 retained prefill/decode GPU-spanning intervals dominate small host encoder/preparation spans but do not prove paging, residency or a kernel cause.

Hypothesis: prepare an explicitly bounded residency set for the existing4B lossless-primary payload AND metadata allocations before fresh vision/input preparation, keep it only through one infer request, and release it after all native work drains. Metal's residency request is a preparatory hint, not a guarantee. It may already do the same work automatically; allocation collection, bookkeeping, residency/coverage/cache/cleanup and memory pressure can outweigh any benefit. No speed or physical-residency gain is established.
