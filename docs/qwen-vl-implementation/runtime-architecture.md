# Qwen-VL Runtime Architecture For Garnet

## Runtime Layers

```text
Dataset / request
  -> processor/tokenizer contract
  -> xlang model expression
  -> Garnet model loader
  -> backend partition
  -> executor
  -> serving scheduler
  -> trace/workbench
```

## Request Object

Initial Python-side request shape:

```python
{
    "request_id": "...",
    "image_path": "...",
    "prompt": "...",
    "processor": {
        "input_ids": ...,
        "attention_mask": ...,
        "pixel_values": ...,
        "image_grid_thw": ...,
        "chat_template": "..."
    },
    "generation": {
        "max_new_tokens": 32,
        "temperature": 0.0,
        "do_sample": False
    }
}
```

Early Garnet can consume processor dumps generated by HF. Later Garnet can own preprocessing.

## Model Load Flow

```text
load config
load tokenizer/processor metadata
load safetensors index
validate xlang model expected weights
partition backend ops
create engine/cache artifacts
bind weights
```

Important rule:

```text
Weight validation comes before runtime execution.
```

If a weight shape is wrong, the test should fail before any CUDA/TensorRT work starts.

## Backend Partition

Initial partition policy:

| Region | First backend | Later backend |
| --- | --- | --- |
| Dense linear / MLP | TensorRT or Garnet tensor op | fused TensorRT/custom CUDA |
| Norm | Garnet op | fused CUDA/TensorRT plugin |
| Vision patch embed | TensorRT | custom CUDA if needed |
| Vision varlen attention | custom CUDA/open op | FlashAttention-style kernel |
| Multimodal merge | custom CUDA/open op | fused scatter/gather kernel |
| MRoPE | custom CUDA/open op | fused with attention where possible |
| Text prefill attention | CUDA/open op | FlashAttention/paged prefill |
| Decode attention | CUDA/open op | paged attention |
| KV update | custom CUDA | paged KV manager |
| LM head | TensorRT/Garnet matmul | fused/top-k later |

## Execution Stages

### Stage 1: Preprocess

Owner: Python/HF first.

Outputs:

- `input_ids`
- `attention_mask`
- image tensor or pixel values
- image grid metadata
- prompt template text

### Stage 2: Vision Encode

Owner: Garnet.

Inputs:

- image tensor
- vision weights
- image grid metadata

Outputs:

- visual embeddings
- optional deepstack features

### Stage 3: Multimodal Merge

Owner: Garnet.

Inputs:

- text embeddings
- visual embeddings
- visual placeholder positions
- MRoPE metadata

Outputs:

- merged hidden states
- position ids
- attention metadata

### Stage 4: Text Prefill

Owner: Garnet.

Inputs:

- merged hidden states
- decoder weights
- position ids
- KV cache allocation

Outputs:

- logits for next token
- populated KV cache

### Stage 5: Decode

Owner: Garnet.

Inputs:

- sampled/selected next token
- KV cache
- position metadata

Outputs:

- token stream
- final text

## KV Cache Position

VLM still needs KV cache for the text decoder.

Even if the image changes often, the decode loop benefits from KV cache after prefill. Reuse can also apply to:

- fixed system prompt prefix
- repeated image/prompt context
- same frame with multiple verification prompts

Early design should separate:

```text
prefix cache
visual embedding cache
decoder KV cache
```

Do not rely on visual cache as the only performance story. Fresh-frame path matters most.

## Trace Events

Garnet should emit JSONL trace events compatible with Workbench:

```json
{"event":"stage_start","node_id":"vision.encoder","ts_us":0}
{"event":"stage_end","node_id":"vision.encoder","duration_us":12345}
{"event":"tensor_snapshot","node_id":"merge.visual","shape":[1,1024,2048],"dtype":"fp16"}
```

Trace categories:

- model load
- weight validation
- preprocess
- vision encode
- multimodal merge
- prefill
- KV update
- decode token
- snapshot
- error/fallback

## Windows And Linux Notes

Windows:

- `garnet.dll` must be discoverable.
- Python tests should use `os.add_dll_directory`.
- xlang module import should print exact DLL path.

Linux:

- shared libraries should use rpath or explicit env setup.
- CUDA/NCCL paths must be documented.
- serving benchmarks should run under predictable container or venv setup.
